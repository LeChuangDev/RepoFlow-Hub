### 调研来源与 10 条结论（已固化到原型「功能缺口」页底部表格）
GitKraken Workspaces（分组 + 批量 pull/fetch/open + 跨设备配置）／竞品对比（GitKraken 免费版仅公开库、私有库要付费；Fork 分离工作区与历史；Sublime Merge 以速度/搜索见长）／Git 多远端实践（单 remote 多 pushurl 的 fetch 只认第一个、错误堆叠、认证过期难定位、失败不重试；独立 remote 可双向）／**Gitee 帮助中心「仓库镜像管理」**（Push/Pull 方向、最短 5 分钟、**不支持 Git LFS**、会覆盖目标分支/标签/提交、双向镜像官方标注有代码丢失风险、>30 分钟超时）／Gitee 官方博客与 MCP Server（API v5、令牌需 projects/pull_requests/issues 权限）／GitHub Docs 细粒度令牌（限定仓库 + 最小权限 + 强制过期 + OS 密钥链；私有资源 404 可能是权限不足）／GitHub REST 最佳实践（优先 Webhook、ETag + If-None-Match 304 不计主要限流、串行且变更请求间隔 1 秒）／Git git-status 文档与 Scalar（fsmonitor + untrackedCache 在 30 万文件级把秒级降到毫秒；commitGraph.changedPaths；git maintenance；网络盘/WSL 下 fsmonitor 失效）／命令面板 8 状态与 Linear（禁用命令灰显说明原因、无结果给恢复路径、离线时本地命令仍可用、模式前缀）／Design for Power Users（批量操作需真实撤销、保存视图要可寻址 URL）。

### 本机只读性能体检（本轮实测，`--no-optional-locks` 不写 index）
git 2.55.0.windows.3；6 仓 status 三次数中位数：32_Demo 35.8ms(861 文件)、Templates 44.4ms(530)、嘉立创资料 24.1ms(6)、lechuang-site 29.7ms(183)、calcbridge 28.4ms(181)、pcb-basics-notes 27.2ms(3)。**全部未启用** core.fsmonitor / core.untrackedCache / commitGraph.changedPaths；6 仓全是单一 GitHub origin，无 Gitee、无多 pushurl。
**反直觉结论**：网上「两行配置 17.6s→0.8s」是 30 万文件场景，照搬到当前规模不成立。真正开销在逐仓串行（合计 ≈190ms，100 仓约 3s）、远端 API 限流、大列表渲染。因此 git 加速配置列为「规模上升后可选」，优先做并发 4 路、缓存 TTL、ETag 条件请求、串行间隔 1 秒、虚拟列表。

### 联网调研（3 组）
- **GitHub 官方 OAuth 文档**：优先建 GitHub App；Web 授权码流程带 `client_id / redirect_uri / scope / state / code_challenge(S256) / code_challenge_method`；公共客户端（桌面 / CLI / SPA）**无法保管 client_secret，必须 PKCE**；设备流仅用于无浏览器受限环境，官方最佳实践明确「不要无故启用设备流」（无 redirect_uri、易被用于钓鱼）；可配置过期令牌（访问 8 小时 / 刷新 6 个月，`offline_access`）；刷新令牌与访问令牌分开存平台推荐机制；应用绝不应把 PAT 当应用认证方式。
- **Gitee 官方 API v5 OAuth 文档**：`GET /oauth/authorize?client_id&redirect_uri&response_type=code[&scope]` → 回调 `?code=&state=` → `POST /oauth/token` 带 `client_secret`（**建议放请求体**）；scope `user_info / projects / pull_requests / issues / notes / groups`；授权码一次性；请求过快会被终止；**未见 PKCE / 设备流**。
- **开源公共客户端的密钥困境**：开源二进制里烘焙 client_secret 不是秘密（可提取、所有用户共享、轮换要发版）。正解是 public client + PKCE + 每用户令牌存系统密钥链；Client ID 可公开。BYOA/BYOK（用户自带应用凭据）是开源工具的默认；托管 broker 更方便但要运营可信基础设施。多账号同 provider 令牌必须分别存；`invalid_grant` 要有重新授权路径，不能无限重试。

3. 开源分发 → 默认 BYOA，不内置共享 client_id/secret；`.env.example` 占位、真实 `.env` 进 .gitignore。

## 同日 v7：联网调研后的可量化性能优化（16:11–16:35）

用户要求继续学习先进案例、优化并**提高性能**。本轮把重点放在可测量的性能提升，而非继续堆功能。

### 调研来源与结论
- `content-visibility:auto` + `contain-intrinsic-size:auto <高度>`：浏览器跳过视口外子树的样式/布局/绘制；有实测 3000 复杂卡片首屏 2840ms→420ms、Layout 1420ms→85ms；必须配 `contain-intrinsic-size`（否则滚动条跳），`auto` 关键字让浏览器记住真实高度。坑：`contain:paint` 裁剪溢出、为 `position:fixed` 建立新包含块、页内查找找不到未渲染内容。
- `content-visibility:hidden` 可缓存 SPA 视图渲染状态，比 `display:none` 切换更快（Facebook 测约 250ms）——本轮因布局风险未采用，保留 `display:none`。
- DOM 预算：理想 <800 节点、上限 1400；虚拟滚动让一万行只留约 25 个 DOM；只渲染激活的 tab（隐藏面板仍在 DOM 里参与样式计算）。
- 事件委托：父容器单个监听器替代逐项绑定，降低 INP；IntersectionObserver 替代 scroll 监听，用完 disconnect。
- 时间切片：`requestIdleCallback` + `deadline.timeRemaining()`（长任务 >50ms 被标记）、`requestAnimationFrame` 对齐帧、`DocumentFragment` 批量插入；桌面应用首屏不做重初始化、非关键逻辑延后。
